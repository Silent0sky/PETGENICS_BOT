# Petgenics Bot: Easy Deployment Guide

Follow these steps to put the bot online with GitHub and Render. You do not need to edit Python code.

## Before you start

Have these ready:

- A GitHub account with access to [`Silent0sky/PETGENICS_BOT`](https://github.com/Silent0sky/PETGENICS_BOT).
- A Render account. Render may charge for the web service and PostgreSQL database; check the current prices before creating them.
- A Telegram bot token from BotFather. **The token previously shared in chat should be revoked. Create a replacement and never send it in chat or put it in a file.**
- Your real party codes from your ERP, plus your product Excel file.

The GitHub repository is currently public. To make the source private, open the repository, go to **Settings → General → Danger Zone → Change repository visibility → Make private** before deploying. Do not upload `.env`, passwords, bot tokens, customer files, or Excel workbooks to GitHub.

## 1. Check the code on GitHub

1. Open [`https://github.com/Silent0sky/PETGENICS_BOT`](https://github.com/Silent0sky/PETGENICS_BOT).
2. Select the `main` branch.
3. Check that you can see `render.yaml`, `Dockerfile`, and `README.md`.

The application code is already pushed. Do not upload the `.env` file or the source Excel files.

## 2. Connect Render to GitHub

1. Sign in at [Render](https://render.com/).
2. Choose **New → Blueprint** (sometimes shown as **Blueprint Instance**).
3. Connect GitHub if Render asks. Allow Render access to `Silent0sky/PETGENICS_BOT`.
4. Select the `PETGENICS_BOT` repository and branch `main`.
5. Review the resources listed in `render.yaml`:
   - Web service: `petgenics-order-bot`
   - PostgreSQL database: `petgenics-postgres`
6. Review Render's plan and price. Continue only if you accept the current charges.
7. Click **Apply** or **Create Blueprint**.

The web service uses Docker. On startup it runs the database migration and then starts the web app. The PostgreSQL database keeps orders and product/party data across restarts.

## 3. Set the Render environment variables

Open the new Render **web service** → **Environment**. Set/check these variables:

| Variable | What to set |
|---|---|
| `DATABASE_URL` | Render should connect this to `petgenics-postgres` automatically. Do not replace it with a local database. |
| `BOT_TOKEN` | Paste the new token from BotFather directly into Render. Keep it secret. |
| `WEBHOOK_SECRET` | Keep the long random value generated by Render. Do not share it. |
| `ADMIN_API_KEY` | Keep the long random value generated by Render. You will need it to open the admin tools. |
| `HEALTH_CHECK_TOKEN` | Keep the long random value generated by Render. |
| `WEBHOOK_URL` | Set this to the web service's public HTTPS URL, for example `https://petgenics-order-bot.onrender.com`. Use the URL Render shows for your service, not a guessed URL. |

If Render asks for `BOT_TOKEN` while creating the Blueprint, enter it only into Render's private environment-variable form. If the service has already deployed without a token, add `BOT_TOKEN` and verify `WEBHOOK_URL`, then save/apply the environment changes. Render will restart or redeploy the service.

Do not put secrets in `render.yaml`, GitHub, screenshots, support messages, or this guide. If a token is exposed, revoke it with BotFather and replace it in Render.

## 4. Wait for deployment and check the service

1. Open the Render service's **Events** or **Logs** page.
2. Wait until the deployment reports **Live**. The first build can take several minutes.
3. Open `https://YOUR-SERVICE-URL/healthz` in a browser, replacing `YOUR-SERVICE-URL` with the exact Render URL.
4. A working service responds with:

   ```json
   {"status":"ok"}
   ```

5. If the deployment fails, open the latest deploy's logs. Check for:
   - `DATABASE_URL` missing or database not ready.
   - Invalid `BOT_TOKEN`.
   - `WEBHOOK_URL` not matching the Render service's HTTPS URL.

After changing environment variables, wait for the service to restart and check `/healthz` again.

## 5. Open the admin page

1. Visit `https://YOUR-SERVICE-URL/admin`.
2. In Render, open the web service → **Environment**.
3. Find `ADMIN_API_KEY` and copy its value privately.
4. Enter it in the admin page and click **Use key for this tab**.
5. Do not share the key. If you think it was exposed, replace it in Render and save the change.

The admin page is public, but admin data-changing API requests require the admin key.

## 6. Import parties and products

Use the protected admin page at `/admin`:

1. **Parties:** use a workbook with your actual ERP party code and party name. Click **Preview and map columns**, check the worksheet and detected header, map the party code and name, then click **Import/update parties**.
2. **Products:** select your product workbook, click **Preview and map columns**, and map product code, product name, brand/company, MRP, pack size, selling rate, and stock where those columns exist.
3. Review the created, updated, skipped, and failed rows. Download the row error report if the page offers one.
4. Use the template and export buttons to get blank templates or download the current database lists.

**Important:** use stable ERP party and product codes. The previously prepared `PARTIES_IMPORT_READY.xlsx` uses generated internal party IDs, not real ERP/MARG codes. Do not use those IDs for MARG export unless you deliberately reconcile them with the ERP.

Blank cells do not clear existing values. Re-importing the same code updates that record instead of making a duplicate.

## 7. Add and approve salespeople

1. Open `https://YOUR-SERVICE-URL/docs`.
2. Click **Authorize** and enter `ADMIN_API_KEY` as the `X-Admin-Key` value.
3. Use `POST /admin/imports/assignments` to import salesperson Telegram IDs, names, authorized party codes, and brand assignments. Follow the endpoint's form fields and mapping in `/docs`.
4. New salesperson accounts are inactive until approved. Use `PATCH /admin/salespersons/{telegram_user_id}/approval` with `{"active":true}` to approve an account.
5. Only assign parties and brands that exist in the imported active party/product lists.

Keep the admin key private while using `/docs`; log out/close the page when finished.

## 8. Test the Telegram bot

1. In Telegram, open the bot created with BotFather and send `/start`.
2. If the salesperson is approved and has assignments, try `/order`.
3. Submit a small test order and check that it appears in the admin page.
4. If Telegram does not respond, check that `BOT_TOKEN` is valid, `WEBHOOK_URL` is the exact public HTTPS service URL, and the Render service is **Live**.

The bot cannot create real business orders until salesperson permissions and party/product data are configured.

## 9. Backups and future code updates

- Use Render's PostgreSQL backup/restore features. Product lists, parties, orders, and drafts are stored in PostgreSQL, not on the temporary web-service disk.
- To update code, make the changes locally, run `python -m pytest -q`, commit and push them to the GitHub `main` branch. Render will deploy the new commit automatically if auto-deploy is enabled.
- Before a production launch, test the bot, imports, approvals, order submission, and database recovery with non-production data.
